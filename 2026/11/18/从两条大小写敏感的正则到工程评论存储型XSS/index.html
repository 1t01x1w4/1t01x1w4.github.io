漏洞简述

某厂商 EDA 产品用户中心的「工程评论」功能存在存储型 XSS。评论内容在服务端原样入库、读取接口原样返回，前端渲染时只用两条自研正则做过滤：一条把图片标签从正文里抽出来单独渲染，另一条按标签白名单过滤。两条关键正则都是大小写敏感的，而浏览器解析 HTML 不区分大小写——只要把标签名写成大写，就能同时绕过「提取」和「删除」，带着 onerror 进入 innerHTML 执行。评论对工程内所有成员可见，且工程负责人可以把任意用户直接加为成员、无需对方确认，因此这条评论可以被定向投递：受害者打开工程详情页，脚本就在其登录态下跑起来。

复现过程

复现环境

  • 两个自有测试账号：一个当攻击者，一个当受害者；
  • 攻击者账号自建一个空工程（下称 <PROJECT_UUID>）；
  • 受害者账号保持默认设置：个人资料里的「自动加入学校/团队/工程」为开启状态——这是后面能直接把人拉进工程的前提，步骤四会展开；
  • Chrome + DevTools 即可，不需要 Burp；
  • 域名统一写作 u.XXX.cn。

有两个前置背景需要先讲清楚，否则后面的代码会显得莫名其妙。

第一，为什么不用页面上的评论框。 评论输入框在提交前会先做 HTML 实体转义（把 < 变成 &lt;），直接在框里写标签，存进去的就是转义后的文本，永远不会执行。而攻击者本来就不受前端输入框限制——他可以直接调接口。所以下面的 payload 走 fetch，这既是最短路径，也贴近真实的攻击方式。

第二，为什么代码里要自己取 xsrf。 这个站点的后端是 Laravel 风格的双提交校验：服务端下发一个 XSRF-TOKEN Cookie，前端在 POST 请求里把它原样放进 X-XSRF-TOKEN 头。这个 Cookie 特意没有设 HttpOnly，就是给 JS 读的——这也意味着后面的 XSS 不光能读页面，还能直接发 POST 请求（这点在「危害」里会再提一次）。

步骤一：创建测试工程

  1. 登录 https://u.XXX.cn，进入「工程 → 所有工程」；
  2. 点击「新建工程」，填写名称、版本任选，勾选「允许评论」，点击创建；
  3. 创建完成后进入工程详情页，记下地址栏里的 project 参数（32 位十六进制）。

评论开关也可以先不勾，创建完在工程设置里再打开——但勾在创建时最省事，后面不用再发一次更新请求。

小坑一：中途试过用 fetch 调接口的 payload，被云 WAF 判定成攻击行为，直接返回 418 拦截页。后续都退回纯前端标记的写法，并控制提交频率。

小坑二：一开始用改 document.title 做证据，有些页面会在脚本执行后重新设置标题，标题会回退，容易被误判成”没执行”。所以横幅比标题更稳，两个一起用最好。

接口语义很直接：uuid 是要加的人，role: 4 是工程里最低的那档角色（只有读权限）。返回 200 {"success":true,"message":"添加成功"}——整个过程不需要对方确认，人就直接进工程了。这是整条链从”自 XSS”升级成”能打别人”的关键：投递不需要社工，只要知道 uuid。

  1. 受害者账号登录后能看到自己已被加入该工程，点进工程详情页，评论渲染，payload 在其登录态下执行。

为什么连确认都省了？ 一开始我以为是接口写得糙，后来在个人资料页找到了答案。页面底部有一个「自动加入学校/团队/工程」的开关，对应接口字段 info.auto_join，默认值是 1（开启）。开关下面的说明写得很直白：

开启后，别人邀请你进入学校/团队/工程时，将自动加入其中。

也就是说，”要不要确认”这件事被交给了用户侧的一个总开关，而且默认放行；接口因此不再做二次确认。/api/user 返回的 info.auto_join 就能看到当前状态，测试账号是 1。

这个细节对复现影响很大，值得单独说清楚：

  • 受害者保持默认设置时，members/add 一条请求就能把人拉进来，攻击者全程不需要和受害者发生任何交互；
  • 如果受害者手动关掉了这个开关，邀请会退化成”待接受”，需要对方在通知里点一下才生效——投递链仍然成立，只是多了一道门槛；
  • 所以严格说，这是一条依赖默认配置的投递链。但”默认配置”本身就是产品设计的一部分，绝大多数用户不会主动去动它，这也是这条链在真实场景里成立的原因。

为什么这条 payload 能执行

payload 能落地，靠的是前端渲染时那两条正则留下的缝。翻到评论组件：

这段代码要拆开看，不然很容易只记住”有个白名单”。

Xt 是干什么的。 评论支持贴图，前端想把图片和文字分开渲染（图片进缩略图组件，点击可放大），于是先用第一条正则 /<img.*?src="(.*?)".*?>/g 把所有 <img ... src="..."> 的地址提取出来，再用第二条 /<img.*?(?:>|\/>)/g 把图片标签从正文里整段删掉，剩下的纯文字才交给后面的白名单。换句话说，Xt 的本意不是过滤，而是拆分——这是它后来出问题的根源：拆分逻辑天然假设”图片一定是小写 img”，而这个假设没人验证过。

RZ 是干什么的。 它是真正的白名单：r = ["p","img","a","br"]，然后构造了一个带负向前瞻的正则 <(?!/?(${r.join("|")})\b)[^>]*>。翻译成人话：匹配所有 <...>，但如果这个 < 后面紧跟的是 p、img、a、br（可带 /，即闭合标签），就不匹配——也就是”留下白名单标签，删掉其他标签”。注意它只删标签本身，不清理标签上的属性，所以 img 上的 onerror 会被完整保留。

问题出在标志位上。 Xt 的两条正则结尾都是 /g，没有 i；RZ 结尾是 "gi"，有 i。JS 正则默认区分大小写，而 HTML 规范里标签名是不区分大小写的——浏览器认 <IMG>，但 Xt 不认。

所以同一条链路，大小写的结果完全不同：

  • 小写 <img ...>：Xt 第一条正则命中，src 被提取成图片；第二条正则命中，整个标签从正文里被删除；RZ 拿到的是空字符串，渲染为一个空 div。这一步我当时没有单独截图，但把 Xt/RZ 抄到 Node 里跑一遍就能复现同样的结果。
  • 大写 <IMG ...>：两条正则都因为区分大小写而没命中，原始字符串原样进入带 i 的 RZ，命中 img 白名单被保留；最终交给 dangerouslySetInnerHTML，浏览器按 HTML 规范解析（标签名大小写不敏感），就是一个标准的图片元素；请求 y 失败，onerror 触发。

危害

  1. 会话内接管：脚本以内置会话调用全部业务接口，不需要密码。可以改成员角色、转移工程负责人、读取工程正文与附件，效果等同于拿到受害者的操作权限。
  2. 工程与设计资产被窃取：EDA 的核心资产就是工程和设计稿。一次 XSS 就能把受害者名下的工程批量加人、转移或导出，属于核心业务数据泄露。
  3. 蠕虫式传播：payload 可以遍历受害者可见的工程，向开启评论的工程继续投放同一条评论，扩散到其协作者，投放成本几乎为零。
  4. 可信域钓鱼与持久化：脚本能把页面替换成「登录已过期」的表单，域名是官方用户中心；评论长期存储，受害者每次打开工程都会再次执行。

修复建议

  1. 服务端白名单清洗（根本修复）：评论入库前用成熟库处理（HTMLPurifier / DOMPurify 服务端版 / OWASP Java HTML Sanitizer），只保留 p、br、a、img；禁用全部 on* 事件与 style；href/src 仅允许 http/https，拒绝 javascript:、data:、vbscript:。不要依赖前端过滤。
  2. 前端统一净化入口：用 DOMPurify.sanitize() 替换自研的 RZ / Xt；如果短期保留自研实现，至少给两条正则补 i 标志，并对白名单标签做属性白名单，innerHTML 只允许走一个统一的 safeHtml() 出口。
  3. 渲染去 HTML 化：评论正文按纯文本存储与渲染（textContent），图片改为独立的结构化字段（images[]）由组件渲染，不要把 HTML 字符串拼进 innerHTML。
  4. 加成员改为邀请确认：members/add 增加「对方接受」流程，阻断「直接把受害者塞进工程」这条投递路径。
  5. 补 CSP 兜底：为站点增加 script-src 'self'、object-src 'none'、base-uri 'self'，逐步去掉 unsafe-inline，即使注入也能阻断内联事件。
  6. 回归用例：把 <IMG SRC=x ONERROR=...>、<svg onload=...>、<a href=javascript:...>、大小写混写与双重编码写进自动化用例；重点断言读取接口返回的已是净化后的内容，而不是只在写入响应里净化。
